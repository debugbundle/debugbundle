`interface-parity-remediation.md`. Authorization comes from the existing API/domain
services; browser controls and CLI/MCP adapters do not grant new authority. New code
uses existing routes; no schema migration or production configuration change is needed.

## Intentional authority and presentation differences

- Ordinary/local-auth MCP has 130 tools. Hosted OAuth MCP keeps 23 read-only tools;
  restricted project-agent MCP keeps five minimized evidence tools. Agent credentials
  cannot use member-management operations. Project SDK tokens remain write-only.
- Browser sign-in, provider install/reconnect and checkout use browser authentication;
  automation does not receive browser cookies or silently bypass those flows.
- Local CLI/MCP setup, profile/filesystem work and local verification have no dashboard
  or standalone HTTP equivalent. They orchestrate existing domain/transport behavior.
- Capped API lists remain capped. Cursor APIs use opaque cursors. A bounded limit does
  not prove there are no older records, and cursor pages do not invent exact totals.
- Saved flow windows, retained sample filters and worker specification metadata are
  distinct existing endpoint contracts, rather than claims of new filtering semantics.
- Source/tests/build and installed CLI/upgrade checks qualify the local candidate.
  Browser and provider/live behavior have not been verified. Commits, publication
  and deployment require separate authorization.
