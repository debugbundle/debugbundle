## Required accept sequence

1. Bound raw body and event count first. Authenticate the **current** project or server-writer principal before examining business authority. A `dbundle_anl_` server writer may use `/v1/analytics/deliver`; a browser project token/relay may only submit client-observed events through the ordinary mixed endpoint. Preserve each original mixed-batch index and V1 debug/error shape.
2. Load current project settings, tier, catalog and any approved space/identity authority. Run the same `admitSemanticAnalyticsEvent` policy for both V2 routes. The accepted snapshot is mandatory-protected and stamps origin project, authority, scope/catalog/identity revisions and received time. No caller field may supply those stamps. A declaration-only space plan or disabled SDK capability is never an admission grant.
3. Compare `(project_id,event_id)` against a durable receipt before any write to the raw object. Same canonical protected content can replay only after current credential/authority checks; it returns the original acceptance and charges no quota. Different content is an indexed `event_id_conflict` and cannot change the first object or operation record. Concurrent writers meet the same unique ledger constraint and resolve to one acceptance or a conflict.
4. For a new event, write **only the canonical protected event bytes** to a V2 object key containing project, event ID and its protected content digest. Keep authority/provenance in the database ledger rather than letting a repeated object write alter it. Then, in one database transaction, recheck current source/catalog/policy authority, claim idempotent quota, insert the receipt/operation identity and enqueue a durable worker job that references the immutable object. Commit establishes recoverable ownership. Only then return an accepted receipt. A failed database transaction never creates a receipt; its unreferenced object needs bounded cleanup. A failed object write never reserves quota or acknowledges the event.
5. The worker leases the durable job, fetches the exact protected object, verifies its digest and ledger provenance, rechecks deletion/unlink/revocation fences, and applies projections with idempotent effects before completing the job. Redis cannot independently acknowledge analytics processing. Receipts survive the offline retry horizon independently of shorter detailed-analysis state.

The existing `createWorkerJobStore` can enqueue under a caller-owned `Queryable` transaction, but the V1 S3-plus-queue helper does not satisfy this sequence. V2 needs its own job name, storage ledger, object namespace, retention cleanup and receipt response. The first implementation should keep the negotiated capability disabled until this sequence, mixed-batch behavior and worker ownership are all verified.

## Required red/green evidence

- Lost HTTP response followed by an identical retry: one receipt, one quota claim and one projection; the duplicate carries the original acceptance time/digest.
- Same event ID with different protected content, including concurrent requests: indexed conflict, no overwrite of the first object or business operation.
- Server writer forged as browser/relay, client event forged as business fact, stale catalog/space revision, revoked issuer, absent consent and unknown schema: bounded rejection without authority escalation.
- S3 failure, database rollback after object write, worker lease loss and retry: no fabricated receipt, no duplicate billing/effect and a bounded orphan cleanup path.
- Mixed V1 debug/V1 analytics/V2 client events: original index correspondence, unchanged V1 acceptance and one strict V2 policy service.
- Receipt expiry, quota reset, correction-window boundary, subject unlink/delete and catalog revision change: explicit unavailable/conflict semantics rather than backfilled or stale evidence.

Unresolved before enabling: V2 worker/projection ownership, verified billing-source namespace and distinct financial operation/object keys, individual-erasure/storage-cost qualification for the owner-selected project-lifetime opaque operation identities, production-volume V2 raw-object cleanup throughput, and the rollout order for the ordinary mixed endpoint's required V2 client-observation support. The internal transactional quota/receipt schema and scheduled staged-object plus resumable listing cleanup are implemented and locally tested. These choices must be resolved in code and tests, not inferred from this document.

## Accepted raw-object retention boundary

Before the tenth migration, receipts protected accepted V2 raw objects for up to ninety days and the orphan sweep treated every matching receipt as ownership. Staged-object cleanup handled only failed acceptance. The new accepted-raw path closes that local storage gap while retaining the receipt for transport replay.

The tenth ordered forward migration now adds occurrence time and explicit active/deleting/deleted raw state to accepted receipts, with clean bootstrap/readiness wiring and a conservative acceptance-time backfill for populated predecessor rows. The scheduled retention lane applies the project's existing 1–30-day raw setting from server acceptance time, so a newly accepted offline event is not immediately deleted. It locks the durable job before project/receipt to match the worker, terminally marks unprocessed jobs as lost, and commits a deletion intent before the bounded S3 call. Failed S3 deletion remains retryable after a five-minute per-object delay; later expired objects can progress while one S3 object remains unavailable. The small receipt and business-operation identity remain after raw deletion, so a matching unexpired lost-ACK retry still returns the original acceptance. The S3 sweep and staged cleaner no longer treat a raw-deleted receipt as an owner, allowing a late remote write to be removed. This path is internal and does not enable V2 capture.

The worker-input loader refuses a deleting/deleted receipt. The retention transaction fences a pending, leased or failed job before S3 deletion; an already completed job remains completed. `raw_retention_outcome='job_completed'` records only that the current narrow job finished, not that the future growth-report projections exist. Expired receipts now prune in bounded oldest-first batches only after raw state reaches deleted; a failed S3 deletion keeps its receipt for retry, and the separate project-lifetime business operation key remains. Before enabling V2, report quality must account for the explicit `lost` outcome, full projections must finish before job completion, and cleanup throughput must be measured at the expected volume. Individual erasure and cost qualification remain open.

The existing five-minute per-object retry timestamp is also an in-flight deletion lease. It is recorded with the durable deletion intent before S3 starts and checked again under the receipt lock, so overlapping cleanup owners do not issue duplicate S3 calls. PostgreSQL execution time controls lease expiry and retry; the queued job's scheduled time controls retention eligibility and cannot make a current S3 attempt look stale. A failed or crashed attempt becomes eligible again after the lease expires; the S3 call itself has a ten-second abort bound. This is a concurrency fence, not a claim that multi-worker capacity or the 24-hour lag rule is qualified.

Local PostgreSQL/LocalStack regressions cover completed and unprocessed jobs, real S3 deletion, retry after S3 failure, a stale worker read, late-write sweep, unchanged receipt replay without a second quota claim, bounded receipt pruning with business dedupe preserved, and populated-predecessor migration/readiness. Concurrency/throughput under load and report-quality consumption of loss state remain release gates. An independently leased one-minute semantic-only catch-up job now has a ten-by-100 batch cap and a 30-second start deadline, without changing the six-hour V1 retention lane. Its theoretical cap is 1,000 objects per run; actual sustained deletion rate, competing worker load, retry behavior and backlog drain require measured production-volume qualification before activation. The included Team allowance is 15 capacity units times 250,000 analytics events per month, so the measurement target must account for real paid capacity and bursts.
