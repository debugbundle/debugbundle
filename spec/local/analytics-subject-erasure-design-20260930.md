# Semantic analytics individual subject erasure — implementation design

Status: local implementation design, 2026-09-30. The candidate route is default disabled; no erasure claim is enabled.

Local implementation progress: receipt ownership indexing and a 90-day protected association edge are present through forward migrations 19 and 20. Migrations 21 and 22 add the cutoff task and `erased` raw receipt outcome. A relay-owned request revokes associated epochs, removes matching live contexts, and fences admission and replay. The separately leased semantic catch-up pass deletes exact indexed objects in 100-item pages with per-key retry, then removes subject-bearing funnel facts and receipt references while retaining a minimal replay receipt. Project funnel quality counts erasure tasks. Isolated PostgreSQL/LocalStack tests prove a failed S3 outcome stays pending, a retry removes the exact object and facts, and stale admission/replay fail. Reported S3 deletion is checked by bounded exact-key listing before a receipt is finalized; a still-present key stays retryable. The route is present but default disabled. Late-write/completion concurrency proof, connected-source scope and API/CLI/MCP control parity remain open.

## Boundary

The first release scope is project identity carried by an authenticated first-party relay. A request names a project namespace revision, one `anonymous`, `user` or `account` reference produced by the customer-held HMAC key, and an idempotency UUID. The relay writer fixes the project. DebugBundle never accepts a raw customer ID, browser credential, or caller-selected project. Connected-space erasure must cover every source project before connected reporting is enabled.

An individual erasure is a point-in-time removal. Evidence with the protected reference whose occurrence precedes the committed cutoff is removed. A later affirmative re-grant may use a fresh producer epoch and create new evidence; the old epoch remains fenced. A stale offline event with an old occurrence time cannot restore deleted state. Namespace rotation does not erase old references by itself.

## Durable ownership and correction

1. Record the protected anonymous/user/account references and namespace revision against each accepted identity receipt in the receipt transaction. The index is bounded to three rows per event, shares the receipt's expiry, and never stores a raw identifier or first-party binding hash. A populated predecessor can backfill only references still recoverable from a retained context; receipts without recoverable provenance fail closed until erased or expired.
2. Persist prospective anonymous-to-known association edges independently of the five-minute context. An erasure of a known user also finds prior anonymous evidence linked through its validated association. This closure is for deletion only; it cannot relabel historical funnel subjects or merge known users. If one anonymous reference was shared across accounts, removal of that shared anonymous evidence is conservative.
3. In the same project-serialized transaction, store a subject/cutoff fence, revoke relevant live context epochs, and enqueue a durable erasure task. New admission and worker projection check the fence; report readers exclude affected facts immediately and expose an erasure quality count while physical deletion catches up. A duplicate request returns the same task status; changed content conflicts.
4. The worker processes a bounded page of indexed receipt IDs. It fences each durable job, deletes the exact protected S3 object with confirmed per-key outcomes and retry ownership, then removes subject-bearing facts and receipt references. A minimal receipt/tombstone can remain to reject replay until the normal transport receipt expiry. A failed S3 call never advances the task past its object. A final verification scan proves no matching object or fact remains; late writes and restarted workers cannot recreate them.
5. Project/day/catalog producer totals are deidentified historical accepted-count evidence. They do not contain subject references and remain explicitly named accepted counts; subject-level funnels and future distinct/cohort state remove the contribution or become partial until rebuilt. No exact quality is claimed while an erasure task or lost evidence affects its window. Project deletion cascades the indexes and fences and retains its separate S3 erasure journal.

## Gate

Before exposing the route, prove authenticated relay ownership, idempotency/conflict, before-ACK and worker races, association closure, fresh re-grant versus stale epoch, populated upgrade, page failure/retry, raw S3 absence, fact/report correction, project deletion and API/CLI/MCP parity. The current epoch revocation fence is a prerequisite, not individual erasure. The semantic capability and capture gates remain disabled until this path and the other phase gates pass.
