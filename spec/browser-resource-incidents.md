## Hidden speculative loads

Page-load lifecycle evidence distinguishes a narrow interrupted-preload pattern from ordinary asset failures. A resource event qualifies only when it is opaque, targets a `link` whose normalized `rel` is `preload`, `modulepreload`, or `prefetch`, the page visibility is `hidden`, `prerender`, or `unloaded`, and the page ready state is `loading` or `interactive`.

That combination infers low severity. First-party JavaScript/CSS asset paths may produce a medium-confidence, confirmation-required demotion suggestion; authentication and other non-asset endpoints do not. The suggested matcher includes service/environment scope, `first_party: true`, host plus parent asset path (or the exact path when no safe parent exists), visibility, ready state, tag name, and `rel`. Visible or completed-page failures do not match. The evidence is described as consistent with a browser-aborted speculative load, never proof.

These DOM lifecycle predicates are enforced at hosted ingestion. When any active rule requires them, SDK config withholds the entire rule set so older clients cannot ignore predicates or run a broader drop ahead of a narrower hosted exception. Ingestion evaluates the full set with normal specificity and precedence.

## Page-load notification bursts

Incident identity remains exact per resource host/path/element type. Opaque resource failures share a separate hashed burst key for the same project, service, environment, browser session, page origin/path, resource host and interruption class within a fixed ten-second capture-time bucket. Bucket boundaries may produce two alerts; delayed worker processing never merges later page loads. The existing per-resource notification key and configured cooldown remain independent. Immediate channels must pass both cooldown checks, serialized before the database read snapshot. Missing session/page identity retains legacy behavior. Raw session identifiers and page queries never enter delivery payloads.

Email uses an independent per-incident cooldown and retains each eligible incident in a project/recipient digest. `config.aggregation_window_seconds` sets the window (1–300 seconds, default 10); the first pending digest sets its deadline. Slack, Discord and alert-webhook rules can opt into `config.cooldown_scope: "project"` with `cooldown_seconds` to rate-limit distinct incidents for that rule, separately per environment and severity. Existing defaults remain unchanged. These controls are available through API, CLI JSON config and ordinary MCP. Signed lifecycle webhooks and GitHub automation retain every lifecycle event.

## Correlated recovery failures

Normalization indexes only resource failures and explicitly failed recovery requests/network breadcrumbs with nonempty session or trace correlation. `browser_recovery_events` stores project-scoped hashes and raw-event references, never request payloads or raw correlation values, for at most seven days. Recording and durable rebuild intents commit together; later context-only 404s refresh an existing resource bundle without becoming incidents. Correlation locks coordinate resource grouping and request arrival in either order. Sampling and raw retention continue to govern evidence availability.

Bundle generation queries separate 30-second windows after the three newest retained resource occurrences, at most 50 candidates each, prioritizing indexed correlation matches. It rechecks service/environment, session/trace, request path, response and timing against the retained source. Missing objects are optional; storage outages retry. Older incident-linked request samples remain a compatible fallback.

The Bundle v1 `resource_failure` block may include up to ten sanitized `recovery_failures`. Each must be a `4xx` or `5xx` captured relative request path with explicit recovery semantics such as refresh, renew, retry, recover, signed URL, or presign. The earliest correlated failure leads the diagnosis because it is more actionable than a generic opaque resource error, while the wording states that it does not establish the original cause. Unrelated paths such as a favicon `404` are excluded. Path semantics plus correlation identify a recovery candidate, not proven causality or request origin. Invalid methods or control characters cannot invalidate a bundle.
