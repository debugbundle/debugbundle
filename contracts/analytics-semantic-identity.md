## Scope and credential separation

Catalog scope and identity scope are independent. A project's catalog can belong to a space while its direct browser/mobile observations retain project-local anonymous identity. Capabilities carry required nullable `identity_scope` together with `namespace_revision`, plus explicit `known_identity_allowed`. A direct project token may only use its own project identity scope and never grants known identity, even in custom privacy mode. A copied hash or context ID cannot widen this authority.

New writer creation requires `kind: server|relay`, which is immutable. Server writers use `dbundle_anl_` credentials and may emit only authoritative sessionless server facts under declared purpose policy. Relay writers use a distinct `dbundle_anr_` credential and may emit only client-observed browser/mobile product analytics, manage their source project's first-party contexts and exchange allowlisted continuity. Neither kind grants read/manage access or the other kind's producer authority. Both are project-bound, hashed, reveal-once, finite-lived and revocable through owner/admin management. Existing project/member/agent/OAuth credentials acquire neither role. The server derives principal from its token record, never from a caller-supplied relay flag, header, SDK name or payload.

A relay writer uses the candidate `POST /v1/analytics/relay/events` endpoint, with the ordinary canonical indexed ACK. It cannot call the authoritative business outbox operation. A V1 relay with only an existing project token remains unverified client observation; forwarding through a backend does not upgrade identity authority. Public relay capability responses advertise `principal: relay`, but that response is metadata, not a credential a browser can present upstream.

Admission stamps immutable origin project, effective catalog scope/revision, catalog revision, independently verified identity scope and verification provenance. The provenance values are `project_anonymous`, `first_party_association`, or `server_namespace`. The first never creates a cross-project subject; the second requires the relay principal; the third requires a server writer and an explicitly configured namespace. Workers and readers use this stored scope, never a project's subsequently changed membership, to interpret references. Current membership/revocation still fences processing and access.

## Customer namespace and keyed references

An owner explicitly selects a canonical project/space identity namespace and declares which backends refer to the same user/account database. A namespace revision binds the derivation policy and key fingerprint. Keys stay on customer backends; DebugBundle receives only protected references and versioned authority. No email, IP, device, account name, or coincident raw-ID matching creates an association.

Use a randomly generated 32-byte HMAC-SHA-256 key, with domain-separated, length-prefixed UTF-8 input. The exact preimage is ASCII `debugbundle.analytics.identity`, a zero byte, ASCII `v1`, a zero byte, then five fields in order. Each field has an unsigned 32-bit big-endian byte length followed by its UTF-8 bytes:

1. Scope kind: `project` or `space`.
2. Canonical lowercase scope UUID.
3. Positive namespace revision in decimal ASCII, no leading zeros.
4. Entity kind: `anonymous`, `user`, `account`, or `binding`.
5. The customer's canonical identifier, at most 256 UTF-8 bytes.

The output is `sha256:` plus the lowercase hexadecimal HMAC digest. The tag describes the digest representation, not unkeyed hashing. Do not coerce numbers, trim, Unicode-normalize, case-fold, or invoke object formatters to guess identity. Canonical identifiers are well-formed strings; the integration is responsible for selecting the same exact identifier across its applications. Test vectors in `tests/fixtures/analytics-identity-vectors.json` are synthetic and are required across all language implementations.

`binding` uses a separate random application-session nonce plus the producer epoch, not the application's authentication cookie or access token. Binding references are server-to-server lookup material, never event dimensions, browser storage values, URLs or diagnostics. A key or namespace rotation increments the namespace revision and revokes old contexts/handoffs. It preserves immutable old evidence and reports a continuity boundary; it never guesses a mapping between old and new users. Project-token rotation does not rotate an explicitly configured namespace key.

## First-party identity lifecycle

Strict privacy has no identity context. Standard allows only anonymous continuity. Known user/account references require custom privacy, affirmative consent for client product analytics, a current namespace and the authenticated first-party integration. A server business fact may use an authorized server namespace under its separate business-purpose policy; it does not imply browser consent.

The relay authorizer validates the application's current session and consent for every incoming request. It replaces caller-provided known user/account/namespace values from its server-owned context; it must not trust a context ID, hash or `authenticated` flag supplied by the browser. The normal public relay body carries no upstream credential. With no authorizer, known identity is unavailable. Direct browser/mobile modes support project-local anonymous analytics; installers must use their first-party backend to enable known identity or cross-project continuity. Neither SDK nor DebugBundle authenticates the application's users on its behalf.

The backend-to-DebugBundle relay delivery envelope is project-bound and contains one bounded `events` array plus an optional `identity_context` object with `context_id`, `producer_epoch` and `binding_hash`. One envelope may represent only one first-party application session/context. The backend derives that object after authenticating its own session and consent; a browser cannot choose it or receive the `dbundle_anr_` writer credential. The upstream route rejects browser Origin and an identity-bearing event without a current relay-owned context. Before protected admission the server replaces all submitted anonymous/user/account references and namespace revision with the current context; it never treats those event fields or SDK metadata as identity authority. Without a context, relay delivery remains project-local client observation with null namespace references. The durable receipt must retain the relay writer, context and producer-epoch IDs beside its namespace revision, while omitting the first-party binding secret/hash from the receipt and report dimensions. This envelope is a server adapter, not a second public Analytics product or a browser SDK credential mode.

An accepted context may expire before its durable worker job runs. The candidate worker read uses immutable receipt IDs and producer epoch plus current relay writer/policy, namespace and revocation; it does not require the five-minute context row. Revocation is serialized with the worker's project lock. Project-scoped identity facts may enter a historical project funnel; the reader excludes them if current writer/member, namespace, privacy or epoch authority is unavailable and counts excluded evidence. Connected-space effects and bounded subject erasure still require implementation. An expired context alone does not revoke accepted evidence.

Candidate context routes are relay-writer-only:

| Operation                    | Route                                                | Closed request / response                                                 |
| ---------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------- |
| Create anonymous context     | `POST /v1/analytics/identity/contexts`               | `AnalyticsIdentityContextCreateSchema` / `AnalyticsIdentityContextSchema` |
| Associate anonymous to known | `POST /v1/analytics/identity/contexts/:id/associate` | `AnalyticsIdentityAssociationSchema` / `AnalyticsIdentityContextSchema`   |
| Revoke context               | `POST /v1/analytics/identity/contexts/revoke`        | `AnalyticsIdentityRevokeSchema` / `AnalyticsIdentityRevocationSchema`      |
| Request project erasure      | `POST /v1/analytics/identity/erasures`               | `AnalyticsSubjectErasureRequestSchema` / `AnalyticsSubjectErasureReceiptSchema` |

The erasure request body is at most 4 KiB and contains only the namespace revision, one protected subject kind/reference and an idempotency UUID. The authenticated `dbundle_anr_` relay or `dbundle_anl_` server writer selects its own project. A server writer gains only erasure here, never relay context creation/association/revocation. Browser Origin, a submitted project and extra fields are rejected. A new task returns HTTP 202 with protocol, opaque task UUID, cutoff time, `pending|complete` status and replay flag. Replaying the same request returns the current task status; a conflicting idempotency key returns a generic conflict. The project and portfolio funnel readers exclude matching subjects immediately after the request, including retained anonymous associations to a requested known subject; the bounded worker removes exact S3 objects, facts and subject indexes. The route is currently disabled by default and must remain so until connected-source deletion and control parity pass.

Creation carries producer epoch, binding hash, namespace revision, protected anonymous reference, consent and idempotency UUID. The authenticated writer fixes project/scope; submitted values cannot choose another space. A returned context contains protocol, opaque context UUID, project/scope and revisions, producer epoch, protected references, privacy/consent and issued/expiry times. Its lifetime is at most five minutes. It is metadata, not bearer authority. Lookup must verify current writer, origin policy, namespace/membership, context expiry, binding and epoch before use. The separately leased semantic retention lane physically prunes expired contexts in bounded oldest-first batches and skips locked lifecycle rows; the V1 retention lane is unchanged. Physical pruning is not a substitute for the lookup expiry and authority checks. The local sixteenth migration adds a minimal project-bound revocation fence, backfilled for already revoked contexts, so a matching live relay can replay its revocation acknowledgement after context pruning. The fence is erased on project deletion. The seventeenth forward migration retains immutable context/writer IDs on accepted receipts. The eighteenth retains their producer epoch and a durable project/writer/epoch fence, backfilled from retained context/tombstone rows. A receipt whose epoch cannot be recovered fails closed at worker/report time. Revoking one context fences all contexts from its writer epoch, including facts already projected into project funnels. Bounded subject erasure and connected-space correction still require implementation before activation.

The first internal storage candidate uses forward migration `202609280014_add_analytics_project_identity_contexts` for a current **project** namespace revision/key fingerprint, owner-mutation idempotency and five-minute relay context metadata. The internal namespace service requires the current organization/project owner and an expected revision for configure, rotate or revoke; it retains no HMAC key, and its idempotent replay describes the historical mutation rather than current authority. Candidate owner GET/preview/apply adapters enforce current project-owner member/session auth, bind a read-only current-state preview hash to apply, and accept only a key fingerprint, expected revision and idempotency UUID. CLI and ordinary stdio MCP use the same API client; default API composition still returns `503`. Create/associate/lookup require a current relay writer, current project policy, matching namespace revision, generation and first-party binding hash; known association additionally requires current custom privacy. Revocation remains callable by the current relay writer after project analytics is disabled, and lookup rejects revoked, expired or rotated contexts. The candidate authenticated create/associate/revoke HTTP adapters apply bounded closed bodies and reject browser Origin, but default runtime composition returns `503` before reaching storage. The disabled relay delivery candidate carries backend-owned context into protected ingress and immutable receipts, and worker reads check current authority. Project identity funnel projection remains default-disabled and incomplete; connected-space identity and cross-project continuity remain unavailable.

Association requires the existing anonymous context, exact binding/epoch, current namespace, one known user and optional account reference, consent and idempotency key. The application derives the known reference from its authenticated user. A context may move from anonymous to one known user once; a same-content retry is idempotent, and any different known user/account is a conflict requiring reset and a new epoch/context. Never merge two known users. Record account membership prospectively at its effective association time; an account switch cannot relabel prior events.

Reset, logout, account switch, withdrawal and namespace change synchronously fence SDK-owned unsent work and advance the local producer epoch. Old crypto/config/hook/bridge completions cannot restore identity. `POST /v1/analytics/identity/contexts/revoke` accepts `AnalyticsIdentityRevokeSchema` through the owning relay writer and responds with `AnalyticsIdentityRevocationSchema`. The request binds the context, producer epoch and first-party binding; the idempotent acknowledgement returns only that generation and its revocation time. The first-party backend revokes the old context; successful server revocation fences later admission/exchange and queued/cached access. Already transmitted requests and previously issued capabilities cannot be recalled locally: remote revocation needs server acknowledgement, and unexchanged handoffs otherwise expire within sixty seconds. This is the same honest transmission boundary as SDK delivery. Re-grant requires fresh context, not reuse of the old epoch.

No background identity polling. Refresh is coalesced on demand and respects the capability rate/expiry policy. Waiting captures use the existing protected 16-record/64-KiB/two-second admission budget. Context refresh is not permission to hold raw identifiers, unbounded callbacks or app-owned objects.

## One-time handoff

Handoff transfers authorized anonymous continuity only. It is not login, user/account authentication or permission to submit a business outcome. Destination known identity still requires its own authenticated first-party association. Without an anonymous source context, there is no anonymous continuity to transfer.

The owner allowlists exact source/destination project and HTTPS-origin pairs within the same active space/namespace. Canonical HTTPS origins exclude userinfo, paths, queries and fragments; destination paths are bounded static absolute paths without query, fragment, backslash, percent-encoded ambiguity or dot segments. The server does not fetch a destination URL or follow redirects. Requests cannot choose an unregistered origin or open redirect. Native universal/app links use the same HTTPS allowlist and their first-party backend; no reusable server credential goes into a native application.

`POST /v1/analytics/identity/handoffs` takes `AnalyticsHandoffCreateSchema`. It binds the authenticated source project/context/epoch/binding and validated destination pair. Generate 32 random bytes, encode base64url without padding, prefix `dbundle_ah_`, store only its SHA-256 and return `AnalyticsHandoffReceiptSchema` with `disposition: issued` once. Expiry is at most sixty seconds. An idempotent issuance retry returns metadata with `secret_unavailable`, never a second usable code or recovered plaintext.

The source application transports the one-time code in a dedicated URL fragment, never a query parameter or campaign field. A destination bootstrap consumes and removes the fragment before initializing instrumentation, then sends the code in a POST body to its same-origin backend. This does not imply that arbitrary third-party logging can be recalled. Mandatory SDK/ingress sanitization must recognize all three new token prefixes (`dbundle_anl_`, `dbundle_anr_`, `dbundle_ah_`) before any retention, and the installer must suppress the handoff fragment in its own logs/referrers. The shared privacy corpus includes all three prefixes and a handoff-fragment case. Candidate sanitizer changes are being qualified against it in every runtime; credential issuance remains gated on first-retention, bridge, relay and installed-artifact checks.

`POST /v1/analytics/identity/handoffs/exchange` takes `AnalyticsHandoffExchangeSchema` through the destination relay writer. Exchange is atomic and one-use; verify the destination project/origin, source/destination membership revisions, namespace revision, source context/epoch/binding state, expiry, destination epoch/binding and affirmative destination consent. Failure reveals only a fixed unavailable/conflict reason, never the source identity. Success creates a fresh destination context for the authorized anonymous reference. Any known-user fields in caller input are forbidden. The code itself is excluded from receipts, metrics, logs, bundles and diagnostics after exchange.

Unlink, source deletion, context revocation, namespace rotation and writer revocation fence unexchanged codes. Expired/consumed code hashes have bounded cleanup, separate from identity evidence retention. No code, context UUID or protected hash is a report dimension or membership-management authority.

## Required integrated evidence

Schemas alone do not satisfy these cases: forged/copy-pasted handles; direct-token known identity; relay business spoofing; same anonymous hash in unrelated projects; namespace/key rotation; same-device user/account switching; wrong origin/path; expired/replayed/concurrent handoff exchange; revocation before exchange; revocation between preparation and dispatch; old async callbacks after reset; code redaction before first retention in every SDK/bridge/relay; and access/cleanup after unlink/delete. Authenticated storage and gateway tests must prove them before these routes or SDK features activate.
