# Semantic analytics control protocol

Status: candidate contract; space, writer, project-plan and zero-report space-plan management interfaces are implemented locally. The SDK-config route has a fail-closed, disabled V2 negotiation variant and a gated current-project capability resolver; default composition still disables it, and V2 ingestion activation remains reserved. Space report activation remains pending. See `analytics-semantic.md` for the whole-phase gate. Existing SDK-config, V1 analytics and hosted OpenAI interfaces remain compatible.

## Capability negotiation

An opted-in V2 direct SDK sends `GET /v1/sdk/config` with its existing project bearer or its new server writer bearer and `X-DebugBundle-Analytics-Schema: 2026-09-analytics-02`. A successful negotiated response adds `analytics_semantic` conforming to `AnalyticsCapabilitiesSchema`; the request without that header retains the installed representation. The authenticated principal fixes `project_id` and authority. The server ignores client attempts to select another project through query/body data.

The default local composition returns an explicit `enabled: false`, `unavailable_reason: not_enabled` capability with no producer, purpose, catalog or identity grant for an exact schema opt-in. A candidate current-project resolver intersects the authenticated credential with the live project plan/catalog, settings, tier, writer issuer and business-purpose grant. The route only calls it when separate capability, report and matching delivery gates are all enabled; absent, invalid, expired or mismatched results fail closed. These gates are disabled in default composition, and this candidate does not qualify producer verification or complete report quality. Project tokens retain the installed SDK-config fields plus the disabled capability; a valid `dbundle_anl_` server writer receives only `{analytics_semantic}` and no debug config. A server writer with a browser `Origin`, a relay `dbundle_anr_` credential, an expired/revoked writer, or a missing credential cannot obtain the writer variant. An unknown schema gets `406 unsupported_analytics_schema` only after authentication; negotiated errors and successes are private/no-store. No negotiated ETag is issued. The installed no-header response/cache behavior is unchanged.

Browser project-token preflight must allow the schema header for the same authorized-origin route as existing SDK config. The header's CORS admission only permits negotiation; it does not grant V2 capture or writer authority.

Negotiated responses use `Cache-Control: private, no-store` and `Vary: Authorization, Origin, X-DebugBundle-Analytics-Schema, X-DebugBundle-Analytics-Config`. Do not reuse the existing public CDN config cache or a project-token-only ETag for this representation. A relay serves a separately authenticated same-origin bootstrap with the same protection and `principal: relay`; upstream forwarding never changes that principal into `server_writer`.

The response identifies protocol, project/scope and revisions, separately bound identity scope/namespace and explicit known-identity permission, selected schema, producer/purpose authority, effective privacy/consent/sampling restrictions and numerical limits. `max_event_age_seconds` is the server intake limit (at most seven days), separate from `correction_seconds` for report revisions; SDKs intersect it with their shorter local offline lifetime rather than treating the 48-hour correction value as a send cutoff. Server time and expiry establish a maximum five-minute lifetime. The client measures elapsed time using a monotonic clock and does not extend expiry because of its wall-clock offset. Cache identity includes endpoint, project, credential generation, transport mode and requested schema. Destroy it on init/reset/credential or namespace change. An absent/unknown protocol is unsupported, a network failure is unavailable, and an explicit disabled response is supported but disabled. None authorizes dispatch or V1 conversion.

The candidate server-writer resolver now includes the current active project namespace and identity scope when project privacy permits it; `known_identity_allowed` additionally requires custom privacy. The Node outbox can prepare protected per-fact references offline, but it verifies that exact namespace and known-identity permission from a fresh authenticated capability before sending. Default composition still returns a disabled capability. Server identity receipts retain the authenticated writer ID and worker/read authority checks; neither a payload hash nor a credential-free SDK option grants identity authority.

Precedence is restrictive intersection: local opt-in, locally permitted fields and runtime capability, authenticated server policy, current consent, current catalog, and effective tier bounds. A remote `true` never enables a locally disabled feature. Strict privacy cannot carry namespace authority. Browser/mobile/relay producers are product-only. Server writers remain unsampled and sessionless; explicitly declared product usage requires granted consent, while committed business measurement additionally requires the customer's business-purpose policy. Permission for one purpose never implies the other, and financial operations remain business-only.

Browser V2 uses one startup negotiation plus response piggybacking/coalesced on-demand refresh, at least 60 seconds apart. No periodic timer polling. Pending eligible captures wait at most two seconds within 16 records / 64 KiB charged to the analytics lane. PHP/WordPress use explicit refresh/cache or Cron; no visitor-request config fetch. Expired capabilities fence dispatch until fresh authorization. A negative response cannot disable existing debugging.

## Catalog and measurement plans

`AnalyticsCatalogEntrySchema` freezes static names, immutable revision, bounded description, explicit producer/purpose, observed/committed success boundary, up to 20 typed enum/boolean properties, eight unit-declared measurements and 16 expected SDK/version pairs. Effective property capacity remains the lower project/tier limit. Enum sets have at most 32 unique members. Business facts require the committed server boundary. Metadata declarations are not proof of observed or verified instrumentation.

`AnalyticsPredicateSchema` permits only event-name, event-kind, producer and approved property `in` clauses. A property clause may contain static strings, booleans and null; missing is not null. Closed all/any groups allow three group levels and sixteen total leaves. There is no regex, SQL, evaluator or arbitrary nested JSON. The finite validator limits recursion independently of submitted depth. Activation additionally checks referenced event/property names and enum values against the exact catalog revision.

`packages/analytics-engine/src/measurement-plan.ts` validates finite references and property values against the submitted catalog before activation, including all denominator, funnel and retention predicates. A predicate must have at least one satisfiable branch for one catalog event: event name, producer, event kind and property-value clauses in the same `all` branch cannot borrow compatibility from different events or contradict each other. The static check respects the V2 server-only semantic kind and browser screen-view restrictions; it does not claim instrumentation was observed. Errors contain fixed codes and report indices only (at most 100), never submitted values or raw schema errors. Recognized credential metadata is rejected rather than silently rewritten; mandatory privacy and bounded-management body limits apply to definitions as well as events. This validation does not grant authority or replace effective-tier, prospective-history and revision checks.

`AnalyticsMeasurementPlanSchema` is the full desired scope state, up to 100 catalog entries and 100 uniquely keyed reports before lower entitlement checks. Expected revision zero creates an absent plan; otherwise the current revision must match. Its UUID idempotency key is scoped to principal, target and mutation kind; a reused key with different protected content is a conflict. Preview is read-only, returns a content hash and explicit additions/removals/coverage/capacity effects. Apply requires that hash and matching scope/catalog/membership revisions. No captured samples or subject lists appear in preview.

The internal project-catalog storage foundation uses migration `202609280003_add_analytics_project_catalogs`: one current project row, immutable per-project entry revisions and an append-only idempotent mutation history. An entry's `(project,name,revision)` content cannot be changed; a changed declaration needs a higher entry revision. Current catalog revision advances only when normalized catalog content changes. The store serializes owner/admin mutations under the same project lock as writer management and intersects each event's property count with both the effective tier and project setting. Preview is read-only; apply rechecks authority, revision, protected metadata, preview hash and capacity in one transaction. These internal methods are not yet the public full measurement-plan apply flow and do not enable ingestion, reporting or SDK capability negotiation. The eventual full plan operation must atomically coordinate this catalog revision with report definitions and legacy-funnel entitlement accounting; it cannot bypass the reviewed full-plan API through a separate public catalog write.

The internal project measurement-plan store uses forward migration `202609280004_add_analytics_project_plans` after the catalog migration. It composes catalog and report revisions in one transaction, preserves immutable report `(project,key,revision)` definitions, records an `available_from` timestamp when a report revision is first activated, and keeps historical applied revisions for idempotent replay. An edited or reintroduced report requires a higher definition revision; unchanged active definitions retain their original availability time. A reused report revision also conflicts if the semantic meaning of any catalog event its predicates could match changes; the caller must advance the report revision and start it prospectively. Catalog description, expected SDK coverage and entry-local revision alone do not change meaning. A predicate without a bounded event-name restriction can match later catalog entries, so adding an entry requires a new revision for that report. Preview has no writes and lists report additions/removals/changes plus effective capacity. Its review hash binds actor/content, current catalog-state revision and the effective tier/project saved-report limit and active legacy-funnel count. Apply rechecks those values and fails with a conflict after an intervening change. Active legacy funnels and V2 goal/funnel/retention definitions share the lower tier/project saved-report cap in both create directions; archived funnels do not consume slots. The existing V1 funnel format and reports are unchanged. Current owner/admin access and settings rows are locked for the reviewed transaction. Space plans, verified producer coverage and V2 ingestion remain gated; these declaration records alone do not activate them.

The ninth forward migration `202609280009_add_business_measurement_policy` adds a default-deny `business_measurement_enabled` flag to current and immutable reviewed project-plan revisions. A project plan may set it explicitly; omission means false, including on a later apply. Preview shows the resulting grant and binds it into the review hash. Apply changes it atomically with the catalog/report revision, while replay returns the historical grant without granting current access. Space plans cannot set it true. A business-purpose catalog declaration or server credential alone is never this grant; future admission must intersect the current flag with project settings, live writer authority, catalog and capability. The V2 endpoint and capability remain disabled.

The internal project-only `semantic-analytics-policy.ts` reader now performs that intersection for live server writers and direct project tokens, with exact plan/catalog revision equality, current enabled/privacy settings, effective paid tier-and-capacity-unit limits and the closed currency table. It derives the active organization billing period from locked paid billing state or the UTC calendar fallback and rejects stale/partial paid periods; neither event payload nor handoff caller chooses the quota bucket. Only a live server writer can receive the current business-purpose grant; a direct project token remains client-observed. Its receipt-transaction recheck re-admits the protected event and rejects a change in the original allowance or billing period before using a captured quota limit. Receipt preflight/final hold the owning organization before the project; the policy locks tier, capacity, billing period, settings, declarations, credential and relevant issuer membership through acceptance. It does not authorize relay or connected identity modes. The received clock and correction horizon must be server-owned at the eventual ingress caller; this reader is not yet connected to a public route or enabled capability. Pre-field idempotent plan submissions retain replay compatibility with their old mutation hash when the historical grant is false.

The local project plan management interface now exposes `GET /v1/projects/{id}/analytics/plan` and `POST .../validate|preview|apply` to current project owners/admins through the same storage service, CLI `analytics plan get|validate|preview|apply`, and ordinary stdio MCP `analytics_plan_get|validate|preview|apply`. Current and historical plan reads include their own catalog snapshot, so replay never borrows today's catalog. Current `get` may include at most 300 retained current-entry producer observation rows, each with an exact decimal processed-event count and first/last UTC observation date. Its separate `producer_observations` list includes submitted SDK name/version, with at most 300 rows and `producer_observations_truncated` when more exist. The new fifteenth forward migration stores this aggregate only for subsequently completed jobs; earlier producer totals are not relabeled. Both observation sets exclude historical entry revisions and unprocessed receipts. Submitted SDK metadata is not package authentication; an absent row is missing observation evidence, not a verified zero. Observation does not verify a business success boundary. Neither validation nor apply enables V2 capture or executes a report. These tools are absent from the restricted agent-read and hosted OpenAI tool profiles.

Project ingestion continues to use its own project catalog. No space plan may grant a producer or widen source capture.

The separate internal `analytics-space-plan-store.ts` uses forward migration `202609280005_add_analytics_space_plans` for current and immutable reviewed space-plan declarations. It locks the owning organization/member, sorted source projects, current space, sorted source catalogs and plan in that order. Preview makes no writes; apply binds actor/content, current space revision/mode and every source catalog revision/coverage into its hash and rechecks them in the transaction. Reads require current owner/source management authority, shared-dashboard tier where relevant and unchanged membership/catalog revisions; stale records are not served as current. A twenty-fourth forward migration and internal worker/read path now persist source-bound portfolio facts and return separate per-project results with catalog gaps and conservative partial quality; they never imply deduplicated people across sources. ## Durable delivery

`POST /v1/analytics/deliver` is a new server-writer-only outbox operation. The body is `{events: SemanticAnalyticsEvent[]}`, 1–256 events and 256 KiB total; each event remains at most 16 KiB. The server requires current capability/catalog/policy and returns `AnalyticsDeliveryReceiptSchema` only after durable recoverable ownership. Ordinary mixed `POST /v1/events` retains its canonical indexed ACK and supports opted-in V2 through the same admission service. The outbox endpoint does not accept debug events or client-observed relay traffic.

The local candidate now registers a disabled HTTP adapter for this route. It validates the exact `dbundle_anl_` bearer against current writer authority, derives the hash from that bearer, binds the writer's project, rejects any browser `Origin`, bounds the body and individual events, and maps enabled internal results to the indexed receipt. An enabled hosted adapter claims the current tier's per-writer ingestion rate through the same limiter used by `/v1/events`; invalid events do not consume that claim. A denied claim returns HTTP `429`, `Retry-After` and an indexed receipt with `rate_limited` for each otherwise valid event, without starting protected persistence. Missing rate policy or limiter fails closed with `503`. This per-credential bound does not cap aggregate organization bursts across writers/projects or establish raw-cleanup capacity. The composed runtime `enabled` gate is false; a valid writer currently receives `503 analytics_delivery_unavailable` without persistence. Tests can inject an enabled service to exercise the protected project-only handoff, including one real PostgreSQL/LocalStack lost-ACK replay. This is not V2 capture availability. Enabling requires the full projections, loss-quality, mixed-client route, measured cleanup and current capability gates below. Financial facts remain closed before staging and receipt.

The candidate `POST /v1/analytics/relay/events` uses the same bounded indexed body/receipt and per-credential limiter through a separate `dbundle_anr_` relay-writer principal. It derives the credential hash from the bearer, binds its current writer project, rejects browser `Origin` and server producer events, and uses the protected project-only client-observation handoff. The composed relay gate is false and responds with `503`; enabled injected tests prove current relay authority, receipt acceptance, source rejection and revocation. This does not authorize known identity, cross-project continuity or business outcomes. Context/handoff services and complete report effects remain separate gates.

The adapter stops starting later event handoffs when the API request has timed out or closed. An already-started handoff can still commit after the client receives `503 request_timeout`; the application outbox must keep unresolved records and reconcile by retrying against the receipt. A timeout never implies rejection or permits a fabricated receipt.

The composed `/v1/events` mixed endpoint still rejects a submitted V2 event with `analytics_invalid_event` at its original index while adjacent V1 debug and V1 analytics events remain accepted. A candidate client-observation branch is now wired behind a separate default-disabled dependency. An injected enabled service accepts exact-version V2 browser/mobile events only after project-token authentication and Origin checks, counts them in the shared rate limit, applies the same current project policy/protected S3/receipt handoff as the server adapter, and returns acceptance or bounded per-index reasons in the installed `{accepted,rejected,errors}` shape. It preserves pending V2 items when V1 debug or analytics quota rejects adjacent items. A server producer cannot use that direct-token branch; connected identity authority is still unavailable; the separate relay writer adapter remains disabled in composition. An unresolved persistence failure returns `503 analytics_delivery_unavailable` without claiming durable acceptance, so a caller must retry using its original event ID. This candidate path is not enabled in composed runtime or advertised through SDK capability. The existing V1 ACK and V2 rejection remain the deployed-facing behavior until the complete worker/report, loss-quality and cleanup gates pass.

A delivery receipt includes original submitted/accepted/rejected counts, one error index per rejected item, and one accepted record per accepted index. Accepted records bind the authenticated project, stable event ID, nullable operation reference, SHA-256 of canonical protected content, first acceptance time, receipt expiry and duplicate flag. Every original index appears exactly once. Duplicate event IDs with identical content may be acknowledged as duplicates without charging quota or counting a business effect again. Conflicting content is `event_id_conflict`. The consumer also compares each index/ID/operation to its submitted batch; schema validation alone cannot prove that correspondence.

V2 raw objects use a separate `semantic-events/{project}/{occurred-hour}/{event-id}/{protected-content-digest}.json.gz` namespace. A conflicting event ID must not overwrite the first protected object before the receipt ledger detects its content conflict. The local `buildSemanticAnalyticsRawEventObjectKey` helper produces this key and project deletion covers its prefix; neither helper is a receipt ledger or an enabled ingress path. Only canonical protected event bytes belong in that object; authenticated authority/provenance belongs in the transactional ledger. Failed-acceptance staged objects and late remote writes after staging cleanup have separate scheduled cleanup paths; neither turns an object into an accepted receipt.

Retryable indexed reasons are exactly `rate_limited`, `monthly_quota_exceeded`, and `analytics_quota_exceeded`. Other bounded reason codes are terminal, including unknown codes for forward compatibility. Missing/malformed responses and transport failures retain the entire unresolved batch; they are not accepted records. Reasons never include captured values or validation exception text. A client timeout does not erase server acceptance or release a still-owned client snapshot.

`AnalyticsDeliveryResultSchema` is the cross-SDK local result, distinct from the HTTP receipt: `{status: "received", receipt}` wraps a validated, batch-corresponding server acknowledgement; `{status: "unavailable", reason}` contains one fixed local failure reason and no receipt, error text or submitted values. `deliver()` resolves to this result even for disabled/unsupported capture, missing consent/capability, capacity/unsafe input, authentication, timeout, transport or protocol failure. Unavailable leaves every unresolved outbox record owned by the caller; it is not acceptance or a terminal server rejection. The caller may require policy or credential repair before another bounded attempt. Existing void `track()` and bounded `flush()` behavior remains unchanged.

### Finalized outbox records

`AnalyticsPreparedEventSchema` is the SDK-owned persisted representation, protocol `2026-09-analytics-prepared-01`. It stores project and opaque destination binding, fixed preparation/expiry times, final event/operation IDs, `event_json` and `prepared_content_hash`. It stores no credential. `event_json` is the complete protected V2 server envelope, at most 16 KiB UTF-8, serialized once before caller persistence. IDs, logical business occurrence time, SDK metadata, identity and finalized callback output are inside those fixed bytes. A prepared record expires within seven days of preparation; retry must not extend this lifetime or rebuild an expired event under a fresh identity. Expiry requires an explicit caller-visible reconciliation/failed-record policy.

The event string is compact UTF-8 JSON with the ECMAScript JSON string/number spelling: no extra whitespace, escaped solidus or unnecessarily escaped Unicode, and no duplicate keys. Integers retain their ordinary decimal spelling and all fractional money/measurements are already strings. Object key order need not be sorted; it is preserved from the original serialization. `JSON.stringify(JSON.parse(event_json))` must equal the stored text. Every runtime must pass literal shared byte/hash vectors before writer implementation; invalid Unicode is withheld, never repaired differently on a retry. `prepared_content_hash` is `sha256:` plus lowercase SHA-256 of the exact UTF-8 event string. It detects corruption; it is not a MAC or authority grant. It is distinct from the server's protected canonical content hash in the acceptance receipt.

The destination binding is SHA-256 of compact UTF-8 JSON `['debugbundle.analytics.destination.v1', canonicalEndpoint, lowercaseProjectUUID]`, emitted using double-quoted JSON strings. `canonicalEndpoint` is the configured HTTP(S) API base serialized through the runtime's qualified URL normalization: lowercase/ASCII host, omitted default port, normalized path and no trailing slash. Userinfo, query and fragment are rejected. The cross-runtime URL/JSON vectors remain a freeze gate; do not derive this from a credential or a redirected request URL. Credential rotation preserves the destination while endpoint/project changes require explicit application migration, never silent replay to another destination.

`prepare` first enforces local opt-in, supported server schema, scoped consent/purpose, input and resource bounds. It performs no configuration fetch and grants no remote dispatch authority. It takes a mandatory protected snapshot before retaining any deferred callback work; finalizes the optional analytics-only hook once; and returns `{status:'prepared',record}` or a bounded unavailable reason. A null hook returns `hook_dropped`. The caller can perform preparation before opening its transaction, then insert the prepared record atomically with the business change. Rollback leaves no outbox row, and preparation never queued/sent the event. An unavailable preparation must not crash or force rollback of customer business logic; the application's explicit instrumentation policy decides how to record that gap. Per-language compiled commit/rollback recipes are still required.

`deliver` accepts prepared records, not mutable track descriptors. It checks each record's protocol, identity correspondence, exact-byte integrity, destination, fixed expiry and preparation clock skew (at most five minutes ahead). It validates the entire batch before dispatch: 1–256 records and the actual `{events:[...]}` HTTP body at most 256 KiB, including separators/wrapper. Wrapper/decoded/in-flight copies remain charged to the SDK's existing combined ownership budget. SDK upgrades can read supported prepared versions or return unsupported; they never rewrite old SDK metadata. Current capability, consent, catalog, writer and privacy policy still apply at dispatch. If newly mandatory protection would alter finalized content, return `policy_changed` rather than mutate it under the same ID. Local record failures return `record_expired`, `destination_mismatch`, `integrity_failure` or the existing unsafe/unsupported reason; they never fabricate a terminal server ACK. No hook, sampling decision, identity derivation or time/ID generation runs again.

The reference helpers in `packages/event-normalizer/src/semantic-analytics-outbox.ts` validate decoded bounded record JSON and receipt correspondence. They are not SDK writers, privacy finalizers, credential validators, transaction managers or network senders. Their acceptance of structure/integrity alone cannot authorize delivery. The consumer compares the receipt's project and each accepted original index/event/operation identity to the immutable sent batch; protected server content hashes may differ after server policy. Alternate UUID/hash letter casing must not bypass duplicate identity checks. Only matching durable acceptance permits the application to mark that exact outbox row delivered. Unknown indexed server reasons remain terminal; malformed/local failure leaves unresolved rows owned by the caller. No automatic business-transaction integration is introduced.

`tests/fixtures/analytics-outbox-vectors.json` pins four independently Python-produced finalized strings, UTF-8 byte counts, destination frames and SHA-256 hashes, checked using Node in `tests/contracts/analytics-outbox-vectors.test.ts`. Cases cover Unicode/escaping, maximum integer money/sequence and preserved object-key order. This establishes Python/Node JSON/hash agreement for canonical endpoints, not qualification of every SDK serializer or each runtime's URL normalization.

Transport receipts persist up to 90 days, independent of the shorter analytical detail horizon. Producers may not replay after their receipt expiry without reconciliation. Business-operation dedupe keys are separately scoped to project, namespace, operation kind and protected operation reference and remain until project deletion. Financial reconciliation and subscription-state horizons still need bounded rules. `track`, `flush`, local-file write and beacon acceptance are not outbox receipts. Outbox cleanup occurs only for a matching accepted record; terminal records enter an application-visible bounded failure state.

The internal accepted-raw retention path applies the existing project `raw_retention_days` setting (default one day, maximum thirty) from server acceptance time, so a newly accepted offline event has a processing window; this is independent of the up-to-ninety-day transport receipt. Forward migration `202609280010_add_semantic_raw_retention_state` adds exact occurrence time and active/deleting/deleted raw state; populated candidate receipts conservatively backfill occurrence to acceptance time. The worker locks the durable job before project and receipt, matching projection order, and terminally marks unfinished jobs as lost before S3 removal. The twelfth ordered migration `202609280012_add_semantic_analytics_loss_days` adds a payload-free project/UTC occurrence-day loss count, including a conservative backfill from existing `lost` receipts. The first active-to-deleting transition increments it in the same transaction as terminal job state; a failed marker write rolls both back, and S3 retries cannot increment twice. The marker survives transport receipt pruning and is pruned under current project aggregate retention or project deletion. It is a conservative quality input, not a complete report-quality projection or proof that no other events were lost. A durable deleting state survives S3 failure and prevents stale worker reads; a failed deletion sets a five-minute per-object retry time so it cannot repeatedly occupy the front of a bounded batch. The receipt and minimal business dedupe row remain for replay. After deletion, the orphan sweep can remove late remote writes. The existing six-hour retention job and an independently leased one-minute semantic catch-up job both use bounded batches; catch-up is limited to ten 100-item batches and a 30-second start deadline, and does not run installed V1 retention. Aggregate progress includes failed S3-delete count and earliest selected due time without object/project identifiers; it is not an oldest-remaining-backlog watermark. Current-setting reductions can make previously accepted raw objects due at once, independently of an arrival-rate cap. Expired receipts prune in oldest-first batches only after raw deletion, using a partial expiry index. Project-lifetime opaque business-operation keys remain until project deletion. A completed narrow observation job is not proof that future growth-report projections are complete. Report-quality consumption of loss state, individual erasure and measured production-volume cleanup qualification remain activation gates. Installed V1 retention is unchanged.

The [2026-09-29 local capacity check](../spec/local/analytics-semantic-retention-capacity-20260929.md) deleted 2,000 real LocalStack objects in two capped passes under competing PostgreSQL reads. Its deterministic allowance model shows the 1,000/minute ceiling cannot meet the 24-hour cleanup-lag invariant for an allowed one-hour 10,000/minute burst followed by steady usage at the 99-purchased-unit Team maximum. This is an open activation blocker even though the small local run was fast.

Project deletion has a separate candidate erasure journal in forward migration `202609280011_add_project_object_erasure_tasks`. A project-row DELETE inserts the task in the same transaction, including account/organization cascade; the task survives the row and the worker leases one 100-key S3 prefix page per pass. Partial S3 success reports only confirmed keys, keeps failed keys retryable and never advances the scan cursor past them. A delayed second scan and daily scans through 90 days address late writes. Local PostgreSQL/LocalStack tests cover rollback, cascade, competing workers, pagination, partial failure/retry and semantic-object absence. A 100-project empty-prefix diagnostic measures the baseline request burden in the [capacity report](../spec/local/analytics-semantic-retention-capacity-20260929.md). This is retry ownership, not an individual-erasure SLA or hosted cost qualification; V2 capture remains disabled.

The receipt's five-minute retry timestamp also leases an in-flight S3 delete under the job/project/receipt lock. PostgreSQL execution time, rather than a delayed job's scheduled cutoff, controls this lease and failure retry. An overlapping owner skips the object until expiry; a crashed attempt remains retryable. Local overlap and delayed-schedule regressions pass, but this fence does not raise the minute-cadenced cleanup ceiling or qualify parallel capacity.

The semantic-only catch-up reports aggregate raw deletions, pruned receipts, batches, duration and whether it reached its bounded run/deadline. The worker logs nonempty or possibly incomplete passes without project/event/object identifiers. A full last batch gives only a remaining-work hint, not a verified backlog count. Oldest overdue age, failure counts and paid-burst capacity remain qualification gates.

The local candidate adds forward migration `202609280006_add_semantic_analytics_receipts` for a separate `(project_id,event_id)` V2 receipt ledger, a project/namespace-scope/revision/operation-kind/reference identity table and a staged-object orphan journal. Neither table family changes V1 ingestion. `persistProtectedSemanticAnalyticsEvent` uses the internal receipt store to lock the organization then project, require a current-authority callback and check durable receipt/operation identity before S3. It then writes gzip of the canonical protected event to a content-addressed V2 key with a bounded abort signal. The final project-locked transaction repeats authority/conflict checks, requires the staged key, and commits the shared analytics event quota claim, durable `process-semantic-analytics-event` job, operation identity and immutable receipt together. A retry returns the original acceptance without a second S3 write or quota charge. A changed protected event or second event for the same operation is a conflict. Failed S3 writes and rolled-back transactions leave no receipt or quota; staged rows remain for bounded orphan deletion. `cleanOldOrphans` fences new acceptance while deleting an old unreferenced object and retries failed deletion. The eighth forward migration `202609280008_add_semantic_orphan_sweep_state` persists a resumable S3 listing cursor. Scheduled retention scans at most ten 100-key pages per run, skips objects modified within two hours, checks receipt and pending ownership under the project lock, and marks an old unowned object `deleting` before removal. A failed delete remains retryable; cursor progress wraps so a write completing after an earlier pass can be found later. The current-policy handoff now derives paid capacity limits and the billing period from locked organization state; the lower receipt primitive still accepts explicit internal values. A transactional worker-input loader verifies the exact job, receipt provenance, canonical protected object bytes and digest under project/receipt locks but does not apply projections. This internal path does not authorize a public V2 endpoint; Complete V2 projection processing and revocation fences, individual erasure/storage-cost qualification and enabled mixed-batch ingress remain activation gates. Maximum-volume cleanup tuning is deferred for the first local evaluation. A seventh forward migration adds only aggregate observed-source counts keyed by project/day/catalog entry and producer; the internal durable-job processor checks immutable catalog meaning and completes the job atomically with the count. It currently admits only project scope without identity state, is polled once per worker pass through the durable PostgreSQL queue, and now writes project-only ordered-funnel facts for a partial reader, but does not provide verified-producer evidence or complete growth reports. The existing retention path prunes it under project aggregate retention. No SDK should treat these candidate bytes as a published receipt service.

The internal `persistCurrentProjectSemanticAnalyticsEvent` service captures the supplied project credential context once, loads the current project-only policy, admits the event under that policy and writes canonical protected bytes before the receipt's final transaction. The organization billing period is derived from that policy, not supplied by the handoff caller. The final transaction rechecks the same credential, reviewed grant, exact catalog, allowance and billing period; revocation or period change during S3 write cannot commit quota or receipt. A staged unaccepted object remains eligible for cleanup. The internal persistence handoff now captures received time from its own server clock; an API adapter must still derive the credential hash from authenticated bearer input. The policy derives the inclusive seven-day intake age; an older unchanged retry is acknowledged only against its current locked unexpired receipt and cannot create a new one. The 48-hour report correction/revision rule remains separate. The registered public delivery adapter calls this service only behind its default-disabled gate; no enabled route or SDK capability accepts V2.

Financial facts currently fail closed at both this internal handoff and the lower receipt-store preflight/final boundary before S3 staging, quota or receipt. The accepted project-only operation ledger keys by subject/space namespace, while revenue requires a distinct authenticated billing-source namespace stable across writer rotation and separate for different provider accounts. A client event field, raw provider ID, or writer token hash cannot supply that authority. Before financial activation, bind the verified integration to a durable source namespace, carry it through the protected receipt and operation/object dedupe keys, add the ordered forward migration and current-source recheck, and preserve API/CLI/MCP management parity if the binding is customer-managed. The wire schema's ability to represent a financial fact is not an enabled financial receipt service.

The candidate wire schema permits a non-null `operation_id` only for server business facts. The operation-identity table therefore cannot retain an accidental client/product identifier forever. The owner selected project-lifetime retention of its minimal project-scoped deduplication rows; project deletion removes them. The release gate still needs individual erasure handling, provider reconciliation behavior and table-growth qualification.

## Management and identity authority

Writer create uses `AnalyticsWriterCreateSchema`: immutable `kind: server|relay`, display name, expected revision, idempotency UUID and a 1–365-day lifetime. Server-kind tokens use `dbundle_anl_`; relay-kind tokens use `dbundle_anr_` and can never submit server business facts. Owner/admin of the source project may create/revoke; the plaintext credential is returned once and its hash is stored. Retrying a creation never recovers plaintext. It returns the existing token metadata and a `secret_unavailable` disposition, requiring explicit revoke/recreate if the caller lost it. Project/member/agent/OAuth credentials never acquire server-write authority. Writer revocation is checked at admission, not only on capability negotiation.

`AnalyticsWriterChangeSchema` wraps create/revoke in reviewed-content preview/apply. Revoke supplies writer ID, positive expected collection revision and idempotency UUID. Preview returns protected label, immutable kind, creation lifetime in days, target, collection revision and remaining capacity, with a hash binding actor/project/normalized change. Preview creates no token or database row. Apply requires `{change,preview_hash}` and rechecks management authority, current revision and capacity transactionally. The project collection starts at revision zero. At most ten unrevoked/unexpired credentials consume slots; these slots do not assert that the issuer still has effective authority. Creation stops at collection revision 1,000, while revocation remains possible. List returns current collection revision and at most ten unrevoked/unexpired metadata records, never hashes or plaintext. Historical mutation receipts contain only immutable public metadata.

The local candidate uses 32 random bytes encoded as 43 base64url characters after the distinct prefix, stores only SHA-256 and binds the row to its project and owning organization. Resolution rechecks that organization/project relationship, organization and issuer suspension, current issuer owner/admin authority and existing shared-dashboard entitlement for collaborators. Prefix and persisted kind must match; the validator defaults to server-only and a relay consumer must explicitly request relay authority. Restoring an issuer's permission can restore a still-unrevoked credential's effective authority; permanent invalidation requires explicit revoke. Expiration/revocation and project deletion remain terminal for that credential. No installed project/member/agent token behavior changes.

Migration `202609280002_add_analytics_writers` adds bounded credential metadata, collection revisions and idempotency receipts. Its forward migration and required-table/ledger checks precede candidate runtime startup; no bootstrap upgrade or destructive step is introduced. The local API, CLI and ordinary stdio MCP adapters use the same store. Management routes require current project owner/admin access, member/session authentication, management rate limits and session CSRF. List and preview reveal no secret; apply returns plaintext only on first successful issuance and audit metadata contains only IDs, fixed disposition and revision. Replays return `secret_unavailable`. The API emits private `no-store` responses; invalid payloads are 400, denied changes 403, missing project/optional store 404, and stale/reused conflicting revisions or capacity 409. V2 admission wiring remains pending: no route currently accepts a writer for semantic event ingestion merely because its token primitive/store exists.

Space membership uses `AnalyticsSpaceMutationSchema`: owning organization, name, expected revision, idempotency key, complete unique project set (1–20) and portfolio/connected mode. Current organization roles are owner/member; therefore creation/binding requires the owning organization owner plus management access to every source. A project admin from an unrelated organization cannot bind it. Read access requires current space permission and every source; an explicit subset is a distinct report. Membership locking, audit, deletion fences, source attribution and prospective measurement follow the parent contract.

Space metadata is capped at twenty active spaces per organization and twenty projects per space. At revision 1,000, further owner saves return a capacity disposition; archive and deletion fences can still invalidate membership. These metadata limits do not pool or expand any source project's paid allowances. Reads require active owning-organization membership plus access to every member project, including the existing shared-dashboard entitlement for collaborators. A downgrade fences shared reads without stripping sources. UUID idempotency keys for spaces are scoped to actor, owning organization and target (`create` or existing space ID). A replay returns the original revision snapshot; it is not a current authorization grant. Snapshots used by queued work, cache or artifacts must match the current revision and complete source set at every access boundary.

`AnalyticsSpaceChangeSchema` is a closed tagged request: `save` carries the complete `AnalyticsSpaceMutationSchema`; `archive` carries organization, positive expected revision and idempotency UUID. Create uses the collection endpoint (null `spaceId` in CLI/MCP); existing saves/archive use the item endpoint. Preview returns the protected display name/mode, exact added/removed project IDs, expected/resulting revision and a SHA-256 content hash. It performs no data writes. The hash binds actor, target and normalized change, is not a credential, and never substitutes for current authorization. Apply carries `{change, preview_hash}` and rechecks authority, revision, membership and capacity under the same transaction locks. The CLI flag is `--preview-hash`; MCP uses `previewHash`. Apply never fetches or approves a fresh preview implicitly.

Successful apply returns `{space, replayed}` with the immutable revision result. List returns `{spaces}` (at most twenty); get returns `{space, replayed:false}`. All are strict shared schemas and use private, no-store responses. Invalid requests are 400, denied changes 403, inaccessible reads 404, and stale/reused conflicting hashes/revisions, linked sources or capacity conflicts 409. Archive increments revision, records former sources in the audit snapshot, releases active memberships and fences old reads/jobs/artifacts immediately. It neither deletes source data nor resurrects a namespace. Retrying any change rechecks current access to the original result's source set. Preview/apply requires owning-organization owner and management access to every old/new source; no project, writer or restricted agent token may use management routes. Session requests require CSRF; reads and changes use the existing bounded management rate buckets. Apply success/failure is audit logged with only IDs, revision and fixed reason metadata.

Known client identity requires a separately verified first-party association, even when a client copies an otherwise valid hash. Capability namespace revision alone does not grant identity. Direct project tokens remain project-local and cannot enable known identity; catalog space membership does not join anonymous references. Strict mode stays session-only. See `analytics-semantic-identity.md` and `analytics-identity.ts` for the closed context/handoff schemas and relay boundary. Authenticated lifecycle storage, cross-runtime compiled examples and all new-token privacy corpora remain part of the unfinished freeze gate.

The default-disabled project subject-erasure request uses a current `dbundle_anr_` relay writer and returns an asynchronous task ID without the protected subject. A separate owner/admin `GET /v1/projects/{id}/analytics/identity/erasures/{taskId}` read reports only project/task IDs, cutoff, pending/complete state and completion time. `analytics erasures status` and ordinary `analytics_erasure_status` use that same management read. Task lookup is scoped to current project authority; default composition returns `503 analytics_identity_unavailable`. Status-read parity does not grant member credentials relay write authority or complete connected-source erasure.

## Interface mapping

All adapters invoke the same package domain services. Project plan, space metadata and writer management below are implemented in the local candidate. A project-only ordered-funnel query now has a bounded API/CLI/ordinary stdio MCP adapter over the existing protected project reader, but default API composition leaves it disabled. Its retained facts and unprojected/failed/lost/excluded evidence force partial or unavailable results with unverified source coverage; `failed_events` is a subset of `pending_events` until accepted raw ownership is resolved. This does not establish complete growth-report quality. Report-bearing space plans, catalog discovery and other report types remain reserved; none implies deployed availability.

An owner/admin may request a local candidate retry of one failed semantic event through `POST /v1/projects/{id}/analytics/events/{eventId}/retry`, CLI `analytics jobs retry`, or ordinary stdio MCP `analytics_job_retry`. The internal transaction locks current project authority and the exact accepted receipt, requires active raw retention, matching project/event/content/object job payload, failed status, unexpired job and fewer than three prior explicit retries, then requeues that same job. The route has no body, returns HTTP 202 only for queued work, audits fixed metadata and is disabled in default composition. Retry cannot claim a successful projection or recreate expired/deleted raw evidence. Failed jobs still need operator attention and complete source/rebuild quality before reports can be exact.
