# Semantic analytics contract

Version: 1
Status: contract freeze in progress; new runtime capabilities remain unavailable until their integrated gates pass. Sections describing future services are required behavior, not availability claims.
Scope: opted-in semantic capture and growth reports. Existing AnalyticsBundle V1 remains supported unchanged.

The product remains one Analytics experience. Date-stamped event schema values are internal rollout/reader identifiers; they do not define separate customer-facing products or duplicate reporting surfaces. The currently unpublished JavaScript candidate uses an explicit schema opt-in while its gates are closed. Before the first usable JavaScript release, replace that temporary first-install choice with one documented current setup and an explicit installed-SDK migration path. The known site/app cutover has a 30-day old-analytics-writer window after both installs upgrade, subject to confirming no other active old writers; record actual dates at release. Remove the old analytics collection/processing lane after that window in a separate reviewed change. Retain old report/artifact readers only for applicable historical retention and versioned artifact obligations; never reinterpret old aggregates as verified semantic evidence. Debug event ingestion remains unaffected.

## 1. Compatibility and authority

V1 remains `2026-07-analytics-01`; the additive event protocol is `2026-09-analytics-02`. Both use `event_type: "analytics_event"`; neither enters the eight debug-event union or receives `event_class`. V1 saved funnels remain legacy step aggregates. V1 responses, SDK method signatures, custom/file transport success semantics and hosted OpenAI's twenty-three-tool projection do not change.

`SemanticAnalyticsEventSchema` validates submitted V2 structure. Validation does not establish source authority, project access, allowed property values or privacy. Ingestion independently authenticates the writer, applies mandatory sanitization, enforces local/project restrictions and catalog revision, and stamps origin project, receipt time and authority in a separate stored wrapper. Those server fields are forbidden in client envelopes. A relay is always client-observed even when it forwards with server credentials.

Server business writers use a distinct, project-bound `dbundle_anl_` credential with write-only semantic-event and capability permissions. First-party relay writers use `dbundle_anr_` and remain client-observed; their separate context/handoff operations never grant server business authority. Exact identity and relay boundaries are in [the identity contract](analytics-semantic-identity.md). Only owner/admin management may create/revoke it; hash it at rest and reveal once. Existing project/member/agent/OAuth tokens do not acquire that authority. Browser/direct project tokens and all relays may submit only browser/mobile observations. A server-authoritative event requires the new writer principal; event fields, SDK names, session IDs and opaque identity handles never grant trust. No credentials appear in V2 event JSON.

## 2. Submitted event

All objects are closed. Required nullable fields use explicit `null`. SDKs emit the canonical shape directly; no generalized legacy-shape coercion.

| Field                          | Meaning and bound                                                                                                                                                                                                    |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema_version`, `event_type` | Exact V2 and analytics literals above.                                                                                                                                                                               |
| `event_id`                     | UUID, stable through retry; duplicate ID with conflicting protected content is rejected.                                                                                                                             |
| `occurred_at`                  | UTC ISO timestamp with millisecond precision; receipt time is server-owned.                                                                                                                                          |
| `sdk_name`, `sdk_version`      | Nonempty bounded metadata, not source authority.                                                                                                                                                                     |
| `service`                      | Name/environment (120 chars each), runtime (32), nullable framework (80).                                                                                                                                            |
| `producer`                     | Kind is browser, server or mobile; `stream_id` (UUID) and safe-integer `sequence` are both null or both present. Sequence only orders events from the same declared producer stream; no cross-producer causal claim. |
| `operation_id`                 | Required opaque `sha256:` reference for a server business fact; null for client and server product analytics. Never an email, order ID, provider payload or raw billing ID.                                           |
| `correlation`                  | Nullable UUID session, anonymous/user/account `sha256:` references, identity namespace revision, trace and deploy context. References are protected correlation, never dimensions.                                   |
| `payload`                      | Kind, static name, positive event-definition revision, purpose, privacy, nullable route/screen/session/acquisition context, properties, measurements and nullable money.                                             |

Kinds: `semantic`, `page_view`, `route_change`, `screen_view`, `session_start`, `session_summary`, `journey_marker`. Named semantic events represent business facts; goals/funnels/conversions are definitions over those facts, not automatic duplicate envelopes. Client legacy funnel/convert helpers retain V1 behavior unless the installer explicitly selects V2 and a mapping.

Server capture is semantic-only and sessionless: it never creates visits, devices, page/screen views or session summaries. Optional client-to-server correlation is expressed by protected identity/trace associations, not a fabricated browser session. Browser/mobile events require a session. Screen context is mobile-only; previous route is valid only with a route change; session metrics only with a session summary. Required context must match the kind.

Event names use a bounded static identifier (120 chars); reject dynamic identity values at catalog enforcement. Route context contains a normalized relative route template only, without query/fragment or userinfo. V2 has no raw page title/DOM text. Screen names use the same static-key grammar. Properties contain at most 20 scalar entries and also obey the existing lower tier/project cap; sensitive/reserved keys are forbidden. Names are canonical without whitespace coercion. String property values must match declared enums before retention beyond admission. Numbers belong in dedicated measurements (at most eight), not arbitrary JSON. A serialized event is at most 16 KiB in UTF-8, in addition to per-field bounds; admission must bound input work before parsing.

Client `acquisition` is null when capture is disabled; otherwise it is a closed object with required nullable `landing_route`, `referrer_domain`, `utm_source`, `utm_medium`, and `utm_campaign`. The route is a template, the domain is a lowercase ASCII hostname (punycode permitted; no IP/URL), and campaign labels are protected static keys up to 128 characters. No full referrer URL, query, UTM content/term, click ID or raw handoff code is retained. `trackReferrers=false` disables the entire acquisition object before input traversal. Server events have null acquisition; attribution joins eligible client touches rather than accepting a server-asserted campaign.

A direct browser first touch begins only after current capability and consent permit capture. Its protected acquisition snapshot stays fixed through later route changes and local admission retries; it is attached once to the first transport-admitted fact. If authority or consent arrives after navigation, the client cannot assert the earlier landing or campaign from this touch. A rejected or lost transport event does not prove delivered attribution; reports must retain corresponding coverage uncertainty.

Client audience fields have their own required nullable `client` object: `auth_state`, `device_type`, nullable static browser/OS family keys and integer major versions, nullable BCP-47-shaped language/locale, and `viewport_bucket`. Use the existing V1 auth/device/viewport enums and major-version bound 10,000. No raw user agent. Server events have null client dimensions. Optional coarse geography belongs to the authenticated stored wrapper, derived under project policy; submitted events cannot assert geographic authority.

`financial` and `money` are either both null or both present on a server business event. Financial operations are closed tagged objects: payment has `payment_id` and nullable `subscription_id`; refund has `refund_id` and original `payment_id`; subscription state has `subscription_id`, positive monotonic `revision`, UTC millisecond `effective_at`, status (`trialing|active|past_due|paused|canceled`), billing interval (`day|week|month|year`) and `interval_count` (1–12). Every entity reference is opaque `sha256:` data, distinct from event/operation IDs. Money is the tax-exclusive settled/returned amount for receipts and the discounted total recurring interval price for subscription state. Never derive state by treating a payment as a subscription snapshot. Tax, quantity and discounts are resolved at the authoritative integration before emission, without collecting billing line descriptions.

Financial admission additionally requires an authenticated billing-source namespace bound to the verified integration and stable across writer-token rotation. It is separate from the optional identity/space namespace and cannot be asserted by the event payload. The current project-only handoff and lower receipt store reject financial facts until that binding and distinct durable dedupe keys exist; this does not block non-financial server business facts under the reviewed purpose grant.

The `sha256:` syntax proves only shape. Applications must supply high-entropy opaque references or derive them with a secret-keyed HMAC-SHA256 and a domain-separated project namespace; an ordinary hash of a guessable customer, order or provider ID is not sufficient privacy protection. SDKs validate/sanitize the reference but cannot prove how the application derived it. The receipt store retains only minimal project-scoped operation identity and first-event/content hashes for deduplication; it has no customer reference or financial payload. The owner selected project-lifetime retention of these keys for replay protection: no time-based pruning, with removal on project deletion. Before release, qualify individual erasure handling, retry/reconciliation and storage growth under this policy; do not silently tie it to the 48-hour funnel correction window or the 90-day transport receipt TTL.

Subscription MRR includes active/past-due recurring price until an effective paused/canceled state; trialing contributes zero. Normalize intervals exactly: daily price × 365/(12 × count), weekly × 52/(12 × count), monthly / count, yearly /(12 × count). These are explicitly chosen fixed annualization rules; they are not accounting revenue recognition. Keep rational precision until final display rounding. A scheduled future cancellation affects MRR/churn only at its effective time; absent predecessor state/history remains a coverage gap.

Measurements have a static key, declared unit and canonical decimal string: no exponent notation, leading zeros, negative zero, NaN or infinity; at most 15 integral and six fractional digits, with insignificant trailing zeros removed. Money uses a nonnegative canonical integer string bounded by signed 64-bit maximum, an uppercase currency code and an explicit exponent 0–4. Currency/exponent compatibility is validated against the versioned supported-currency table; syntax alone does not prove a currency is supported. The initial table is `iso4217-2026-09-17`, generated from SIX ISO 4217 Maintenance Agency List One, with 165 currencies/fund codes having a numeric minor-unit exponent. `analytics-currencies.ts` pins the source URL and SHA-256; codes with undefined minor units (including metals/XXX) are excluded. New original operations use the current supported table. Accepted financial state and receipts must retain their table version and exponent; later currency retirement never relabels historical totals or prevents an in-horizon refund of an accepted payment using its original currency. A table update is an explicit reviewed source change, not a runtime network fetch. No automatic currency conversion. Never coerce money through a JavaScript floating-point number. Refund direction comes from the declared event/operation kind, not an ambiguous negative payment. Derived sums use exact decimal/integer arithmetic and an explicit overflow disposition.

`purpose` is `product_analytics` or `business_measurement`. Browser/mobile accept only consent-granted product analytics. Server business measurement requires server authority and the customer's declared purpose policy; it is not a browser-consent bypass. Strict privacy has no anonymous/user/account references or namespace revision. Standard may use only an anonymous reference. Identified user/account references require explicitly selected custom identity integration; hashes alone do not authorize linking. A non-null subject reference requires a positive namespace revision; an empty identity has a null revision. Identity acceptance is additionally bound to the authenticated project/space.

## 3. Catalog and definitions

Executable catalog/definition and capability/receipt schemas are in `analytics-definitions.ts` and `analytics-protocol.ts`. Their exact candidate transport and management semantics are specified in [the control protocol](analytics-semantic-control.md). These additive schemas do not activate routes.

Catalog ownership is a project or one active same-organization space. Each event definition has an immutable revision, static name, description, permitted producer kinds/purpose, typed enum properties and declared measurement units, success boundary and expected producer versions. Owner/admin creates a revision with `expected_revision` and an idempotency key; conflicts return 409 with no partial write. Discovery exposes declared/observed/verified states and counts, never captured examples or subject lists. Unknown properties are withheld; strict enforcement rejects undeclared events. Remotely edited definitions may restrict local collection only.

Predicates use finite typed conjunction/disjunction groups, maximum depth 3, 16 clauses and 32 enum members. No executable expression, user regex, SQL or arbitrary nested captured JSON. New definitions begin prospectively unless retained, authorized, unsampled evidence proves complete historical coverage. Definition changes never relabel old results.

Ordered funnels declare 2–10 step predicates, subject (`session|anonymous|user|account`), one first entry per cohort, sequential ordering with intermediate events allowed, entry-time breakdown, timezone, observation cutoff and a conversion window (default seven days, maximum 30). Distinct steps require distinct events. Equal timestamps without a comparable producer sequence are ambiguous. Entry cohort is `[from,to)`; later steps may occur beyond `to` within the entry window. Mature, open, expired and unknown populations are separate.

Retention declares entry/return predicates, subject, calendar timezone and exact-period or on-or-after mode. D1/D7/D30 and weekly/monthly cells exclude unobserved periods from averages. First use means first observed since `available_from`. Distincts are unions across the requested window, never sums of bucket uniques. Account membership snapshots apply at occurrence time.

Attribution uses first eligible and last non-direct touch, default 30-day lookback, linked coverage and explicit unknown reasons. Internal space navigation does not overwrite external acquisition. Each single-touch view attributes each conversion once. Revenue reports separate currencies, receipts/refunds and subscription MRR. Annual MRR is exact amount/12 until display rounding; totals round after aggregation. Trials/one-offs/taxes do not add MRR; effective subscription state determines cancellation/churn, not webhook arrival order. Provider receipts and subscription state have distinct idempotency keys and reconciliation horizons.

Executable ordered-funnel, calendar-retention and financial calculation semantics and hand-calculated cases are in [the metric contract](analytics-semantic-metrics.md). The kernels are not yet wired to durable projections or public reports.

## 4. SDK surface and lifecycle

Existing `analytics.track/pageView/funnel/convert/marker/setContext/setUserHash/setConsent` and debug `beforeSend` retain their installed signatures/behavior. In the current local JavaScript candidate, V2 is selected explicitly with `analytics.schemaVersion`; omission still uses V1. That selector is a temporary development boundary: the first usable JavaScript release must present one current Analytics setup, with a documented major-version path if installed method meaning changes, while older installed packages and debug capture remain compatible during the upgrade window. Backend/native analytics is disabled by default. No new setting/hook/service is required for existing debugging.

The V2 method family is language-idiomatic:

| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Track              | `analytics.track(name, properties?, options?): void`; `options` has eventId, occurredAt, operationId, sequence, measurements, money and capture context. Existing two-argument calls remain void.                                                                                                                                                                                                             |
| Context            | `analytics.withContext(context): AnalyticsClient`; returns an isolated immutable facade for a request/job, without changing process-global identity.                                                                                                                                                                                                                                                          |

| Consent            | `analytics.setConsent(boolean): void`; synchronous revocation barrier for unsent work, no injected UI. Backend facade consent affects only that scope.                                                                                                                                                                                                                                                        |

Python uses snake_case; Go/.NET exported methods use PascalCase; Java/PHP/Ruby/Swift follow their existing public conventions. Compile examples against every actual interface before contract-freeze completion. An optional new `analytics.beforeSend` is analytics-only, synchronous-return, isolated and deferred, never the existing debug hook. It may change schema-valid event content/ID but cannot grant source authority or widen privacy. Return null drops; invalid/throwing/Promise results preserve the sanitized original; valid replacements revalidate/re-sanitize. Retrying reuses finalized content and does not re-run callbacks or sampling.

Outbox preparation uses the same protected finalization pipeline exactly once. Its explicit asynchronous result is separate from fire-and-forget capture; synchronous runtimes use their documented bounded explicit-call equivalent. No preparation network request, automatic send or application transaction ownership is allowed. Delivery consumes the immutable prepared protocol, checks destination/integrity/expiry and current policy, and never rebuilds SDK version, IDs, occurrence time, identity, sampling or callback output. See the control protocol for canonical stored bytes and transaction/retry semantics. An isolated SDK operation may be implemented behind disabled capability after its exact signature, mode, credential and bounded safety checks are recorded; a partial delivery consumer is not a complete writer family. The first release candidate is scoped to JavaScript browser and Node; other language writers require their own contract and acceptance gates before later activation.

SDK capture performs cheap admission checks before traversing app data, then a bounded primitive snapshot, mandatory sanitization and schema validation before any retention. No pending raw closure, arbitrary getter/enumerator/formatter or caller-owned mutable reference. Recognized credential protection is mandatory with or without callbacks; custom redaction only adds. Invalid/over-budget input is withheld with fixed bounded diagnostics. Import is side-effect-free.

Browser V1's installed sampling decision is once per initialized analytics session; correct the misleading event-sampling prose without changing installed behavior. V2 uses one deterministic subject/session sampling decision for coherent funnels, defaults to 1, and exposes sample policy in evidence. Exact financial totals require unsampled authoritative sources; never extrapolate sampled payments. Journey-example and debug sampling remain independent. Debug fingerprint suppression never drops repeated legitimate analytics facts.

## 5. Resource and delivery ledger

Each runtime has one bounded analytics lane independent of debug failure/quota state. Reuse transport/ACK/privacy code, not debug-only envelope casts or suppression. Analytics-owned pending work, finalized records, retries, in-flight and retired generations all count together. Never silently raise or consume the existing debug capacity. The figures below are analytics ceilings, not permission to allocate that amount in every intermediate stage. The cross-runtime combined ownership design and measured baselines must qualify before contract-freeze completion; a configured process-wide ceiling remains binding.

| Volatile lane                | 256 events / 4 MiB; event at most 16 KiB; expire after 24h, earlier on consent/config invalidation.                                                                                                                                                              |
| Pre-capability/identity work | 16 protected events / 64 KiB, charged to the lane; two-second admission wait, then fixed unavailable disposition. No raw inputs or indefinite callbacks.                                                                                                         |
| Senders                      | One ordinary analytics sender; one lifecycle send where supported. Backend non-PHP analytics work must not occupy the debug sender while stalled. No replacement-worker growth.                                                                                  |

## 6. Capabilities and configuration

V2 clients explicitly negotiate the schema in the existing SDK-config request; legacy response shape remains unchanged. Capabilities are endpoint/project/credential/mode-bound and authenticated, with a maximum five-minute TTL. Separate supported/unsupported/unavailable. A credential-free relay advertises only its authorized browser capability through the same-origin relay integration, never a server writer token. Cache keys/ETags vary with authenticated scope and requested representation. Unknown fields cannot enable a capability.

Browser V1 remains zero-periodic-polling. V2 may use one session-start check, response piggybacking and a coalesced on-demand refresh after expiry with a 60-second minimum interval; no periodic timer traffic. Pending opted-in V2 work is protected and bounded by section 5. No grant/consent means no pending capture. Expired/unavailable capability disables dispatch; never silently convert V2 server facts to V1. Native refresh is lifecycle/on-demand bounded. PHP uses its existing cache/explicit refresh and WordPress WP-Cron; no visitor-request config network call.

All legacy direct, relay and local debug transports continue working. V2 local file capture has no implicit claim of local CLI analytics aggregation; unsupported processing is explicit and cannot be reported as delivered cloud analytics. Self-hosted V2 uses the same contract without contacting DebugBundle cloud. Package mode tests must cover custom transports, every claimed relay adapter, old native binaries with new RN JS and disconnected servers.

## 7. Spaces, identity and threat boundaries

One active space per project, same owning organization, authorized owner/admin on every source. Space reads require space permission and every contributor's current permission. Apply to reports, cache, export, jobs and artifacts; do not trim steps invisibly. Event origin project is immutable and billing remains source-attributed. Joining is prospective, not a historical auto-merge.

Known references are keyed, explicitly project- or space-scoped pseudonyms from an explicitly configured canonical namespace. No identity merge from matching email/IP/device/raw IDs. Authenticated first-party link operation may bind anonymous to known under current consent; never merge two known users. Handoff is one-use, source/destination/space-bound, allowlisted, short-lived and server-exchanged; raw/stable IDs cannot enter URLs. Strip handoff capability from every debug/analytics/referrer/log surface before capture. Logout, account switch, namespace rotation and unlink invalidate future linkage. Strict mode cannot produce cross-session identity reports.

Threat tests: forged writer/SDK/authority, client replay and handle copying, cross-organization membership, missing contributor access, key/token rotation, shared device/account switching, delayed callbacks/jobs after deletion, handoff replay/open redirect, captured prompt injection, cardinality attacks and complementary small-cell disclosure. Management uses existing session/member authorization and CSRF rules; output uses bounded field allowlists. No real server key reaches browser storage, query parameters, examples or diagnostics. Synthetic cross-language HMAC vectors and closed context/handoff schemas are specified in `analytics-semantic-identity.md`; authenticated lifecycle storage and privacy-corpus qualification remain implementation gates.

## 8. Storage, receipts and metric quality

Keep existing Postgres/Redis/object-store boundaries and fenced durable worker ownership. Do not acknowledge Redis independently inside analytics processors. Atomic effects include receipts, quota claims, projection updates and follow-up intents. A lost response/retry may not bill twice. API acceptance must establish durable recoverable ownership before an outbox consumer deletes its record; local queue admission/flush/file/beacon is not that receipt. Duplicate ID with different sanitized content is a conflict. Operation dedupe prevents two transport IDs from counting one payment twice; distinct operations remain distinct.

Identity/cohort detail is capped at 90 days, funnel windows 30 days plus 48h report correction; effective project entitlement may be lower. The negotiated `max_event_age_seconds` is distinct from `correction_seconds`, so SDKs cannot use the shorter report value as an offline send cutoff. Intake derives a maximum seven-day event age from server-owned receipt time, including the exact boundary; callers cannot supply an older correction horizon. An event older than that limit can only replay its original unexpired receipt after current authority/protected-content verification. The existing receipt is locked again before acknowledgement, so deletion or a conflicting event cannot turn the retry exception into a new acceptance. This offline-delivery allowance does not make an already finalized report revision mutable: later eligible evidence needs a new revision with its own received watermark and quality state. The 48h correction value is a report calculation/revision rule, not the ingestion cutoff. Transport retry receipts cover at least the supported seven-day offline horizon. Minimal opaque business-operation dedupe keys remain until project deletion; financial reconciliation and subscription-state horizons still need separate bounded rules, never the 48h funnel cap. Unknown history/expiry returns unavailable/provisional, not zero. Active definitions may not exceed effective retention. Deletion/unlink/revocation fences pending work and cache/artifact access before asynchronous rebuild.

Baseline performance is measured per runtime before changes: repeat filtered and admitted 10,000-record bursts, held senders, absent config and worst-size accepted events; record p50/p95/p99 capture cost, retained bytes and worker progress. The candidate may not increase p95/p99 debug capture overhead more than 10% beyond measurement noise or exceed any count/byte ceiling. A threshold miss requires investigation and owner review, not changing the benchmark to green. SDKs do not guarantee analytics delivery at the expense of the host.

## 9. Public surfaces and rollout

New domain operations have API/CLI/stdio MCP parity and reuse existing domain services. Use `analytics catalog`, `analytics plan validate|preview|apply`, `analytics spaces`, `analytics reports`, `analytics retention`, `analytics revenue` under the existing CLI analytics family. Freeze exact HTTP/tool schemas with the corresponding service before enabling it; no dashboard-only writes. Every mutation is revision-aware and previewable. Hosted OpenAI V1 remains unchanged and aggregate-only.

Forward migrations precede validators/readers and gated workers; writers activate only after authenticated negotiation. Missing migration fails startup/readiness. Old readers/SDKs, mixed batches and populated predecessor upgrade/rollback are required fixtures. No destructive migration in this release. Artifact V2 is separately versioned; V1 artifact bytes/reader semantics remain compatible.

Publish dependency roots before wrappers, use actual registry-backed clean consumers, qualify both RN bridges and assembled WordPress ZIP, then update dogfood pins. A feature is a coordinated additive minor on each current package major; a breaking legacy behavior needs a major/migration. No publication is authorized by this contract. UI follows the separate approved design proposal. Source completion is distinct from package availability, deployment, customer adoption and browser/device acceptance.

## 10. Contract-freeze completion gate

This document and the initial shared validator are a working implementation checkpoint. The owner selected JavaScript browser and Node for the first usable release candidate on 2026-09-29; other SDK V2 writers are deferred and their installed V1 behavior remains supported. An isolated SDK operation may be implemented behind disabled capability after its exact signature, local transport mode, privacy and credential boundaries, and bounded ownership checks are frozen with an executable example. Do not mark the JavaScript SDK slice complete, enable V2 capture or publish the schema until all of the following are resolved for the selected browser and Node modes:

- Exact language signatures/options/result types, configuration precedence and per-family mode/framework/bridge matrix; the TypeScript reference method family above is insufficient on its own.
- Complete client-dimension/campaign, identity handoff, catalog revision and financial-operation schemas; explicitly preserve existing device/audience reporting when V2 automatic capture replaces V1. No implicit dual emission or double counting.
- Exact capability request/response/cache examples, writer lifecycle routes, indexed dispositions, delivery receipts and API/CLI/MCP operation schemas.
